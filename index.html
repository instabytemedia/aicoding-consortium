§ 1

The fragmentation problem

Every AI code engine reads project context from markdown — but each one defines its own file name, its own structure, its own semantics. Teams maintain five copies of the same truth, and none of them are verifiable.

CLAUDE.md AGENTS.md .cursorrules .windsurfrules copilot-instructions.md GEMINI.md spec.md requirements.txt?
──▶
■ product.aicc.md

A single canonical specification file with a normative structure, typed frontmatter, RFC-2119 requirement keywords, and a published conformance suite. Engines translate from AICC — never the other way around.

§ 3

Anatomy of a conforming document

product.aicc.md ✓ aicc validate — 0 errors 
---
aicc: "1.0"
kind: product-spec
id: com.example.checkout
version: 2.3.0
conformance: strict
engines: [claude-code, cursor, copilot]
---

# Checkout Service

## Overview
Cart-to-payment conversion for all storefronts.

## Requirements <!-- @aicc:normative -->
- Payments MUST be idempotent per order id.
- The API MUST NOT expose card data.
- Retries SHOULD use exponential backoff.

## Constraints <!-- @aicc:directives -->
- Engines MUST run `pnpm test` before commit.
- Engines MAY refactor within `/src/checkout`.

Structured for machines. Readable by humans.

  • § 4.1 Typed frontmatter. Identity, semver, conformance class and target engines are declared, not guessed. A parser knows what it is reading before line ten.
  • § 6 RFC-2119 keywords. MUST, SHOULD, MAY carry normative weight. Engines can distinguish hard requirements from preferences — deterministically.
  • § 7 Annotated sections. @aicc annotations mark which sections are normative, informative or engine directives. No more prompt-guessing.
§ 4

Conformance classes

Class A

AICC Basic

Valid frontmatter and canonical section taxonomy. The entry point — any well-formed spec file qualifies with minutes of work.

Class AA

AICC Strict

Every non-canonical section explicitly annotated, every requirement carries exactly one RFC-2119 keyword, zero validator warnings. Machine-verifiable end to end.

Class AAA

AICC Certified

Strict conformance plus round-trip interop proof: the document translates losslessly to and from every engine dialect declared in its engines key.

▸ Reference implementation: the AICC Web Validator — implements the full § 10.3 error taxonomy, runs entirely in your browser. Open the Validator

Reference CLI: node plugins/aicc/scripts/validate.mjs <file> — ships in the aicc Claude Code plugin as /aicc-validate. The conformance test suite is maintained by WG-CONF in conformance/.

§ 5

The agent-native web

When agents become first-class citizens of the web, every origin needs to answer three questions: Where is my specification? What may an agent do here? How do we tell each other? ADP (AICC-TR-006) answers them the way the web always has — a text file, a well-known URI, and HTTP headers.

https://example.com/.well-known/agents.txt ADP/1.0 
# agents.txt — what agents may do here
Engine: *
Spec: /product.aicc.md
Policy: /.well-known/adp.json
Allow: read
Allow: propose
Disallow: execute

# NOT part of agents.txt — the same contract via HTTP:
ADP-Version: 1.0
Spec-Location: /product.aicc.md
Agent-Policy: allow=(read propose)

robots.txt told crawlers where to go.
agents.txt tells agents what they may do.

  • TR-006 §3 Discovery. Any engine landing on an origin finds the governing AICC spec in one request — no guessing, no scraping.
  • TR-006 §3.1 Action classes. read → propose → write → execute — an escalation ladder origins grant explicitly, per engine.
  • TR-006 §4 In-band signalling. Agent-Intent and Agent-Policy headers let origins enforce policy at the edge, per request.

§ 6

Governance & process

Standards earn authority through process. Every AICC technical report advances through four public maturity stages; transition requires implementation evidence and working-group consensus.

STAGE 1

Editor's Draft

Open exploration inside a working group. No standing.

STAGE 2

Working Draft

Published for community review. Breaking changes expected.

STAGE 3

Candidate Rec.

Feature-frozen. Exits to Recommendation with two independent implementations.

STAGE 4

Recommendation

Normative. Versioned. Backed by the conformance suite.

WG-CORE

Core Format Working Group

Owns AICC Core and the frontmatter schema. Meets bi-weekly, minutes public.

WG-INTEROP

Engine Interop Working Group

Maintains translation mappings and the engine registry with vendor liaisons.

WG-CONF

Conformance Working Group

Owns the validator, the test suite and the certification programme.

WG-SEC

Directive Safety Working Group

Reviews agent-directive semantics for injection and privilege-escalation risks.
