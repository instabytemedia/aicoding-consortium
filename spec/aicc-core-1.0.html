AICC Core — Level 1.0

AICC Markdown: a normative format for specification and instruction documents consumed by AI code engines.

Abstract

AI code engines derive project context, requirements, and behavioural constraints from markdown files. Today each engine defines a proprietary dialect (CLAUDE.md, AGENTS.md, .cursorrules, and others), which fragments a project's single source of truth across unverifiable copies. This document defines AICC Markdown: a versioned document model, a typed frontmatter schema, a canonical section taxonomy, normative requirement keywords, and a precedence model for engine directives. AICC documents are valid CommonMark, readable by humans without tooling, and deterministically parseable by machines.

Status of This Document

This is a Candidate Recommendation. The feature set is frozen. Advancement to Recommendation requires at least two independent, interoperable implementations of the full conformance suite (§ 10). Comments are welcome until the end of the candidacy period.

1Introduction

1.1Motivation

Instruction markdown has become the de-facto interface between development teams and AI code engines — yet it has no standard. The same project intent is duplicated into per-engine files, the files drift apart, and no engine can verify whether it has understood a requirement or merely guessed at prose. Three failures follow:

  • Duplication. One truth, five files, zero synchronisation.
  • Ambiguity. "Should probably use retries" — is that a requirement or a remark? Engines cannot tell.
  • Unverifiability. Without a schema there is nothing to validate, so errors surface at generation time — the most expensive moment.

1.2Design Goals

  1. Human-first syntax. An AICC document is ordinary markdown. Reading it requires no tooling; writing it requires no build step.
  2. Deterministic machine semantics. Every construct that carries meaning for an engine is explicitly marked — never inferred from prose style.
  3. Engine neutrality. AICC favours no vendor. Engine-specific behaviour lives in interop mappings (§ 11), not in the core format.
  4. Graceful degradation. An engine that knows nothing about AICC can still consume the document as plain markdown and lose only precision, never content.
  5. Verifiability. Conformance is machine-checkable. "Valid" is a property a validator proves, not an opinion.

2Terminology

The key words MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT, RECOMMENDED, MAY, and OPTIONAL in this document are to be interpreted as described in RFC 2119 when, and only when, they appear in all capitals.

TermDefinition
DocumentA single AICC file: frontmatter block plus markdown body.
EngineAny software that consumes AICC to inform automated code generation, review, or agentic action (e.g. an AI coding assistant or CLI agent).
AuthorThe human or system that writes and owns a Document.
RequirementA list item inside a normative section containing exactly one RFC-2119 keyword (§ 6).
DirectiveA Requirement whose subject is the Engine itself rather than the product (§ 8).
AnnotationAn HTML comment of the form <!-- @aicc:… --> that assigns machine semantics to the section it follows (§ 7).
ValidatorSoftware that checks a Document against this specification and reports the error taxonomy of § 10.3.

3Document Model

3.1File Naming & Discovery

An AICC document MUST use the suffix .aicc.md. The root document of a repository SHOULD be named product.aicc.md and SHOULD reside at the repository root.

Engines MUST discover documents in this order: (1) the file explicitly passed by the invoker, (2) product.aicc.md in the current working directory, then (3) each ancestor directory up to the repository root. In addition, when an engine operates on a path, it MUST load every *.aicc.md document in the directory chain between the repository root and that path (downward discovery). All discovered documents form the implicit composition chain of § 9.

The double suffix is deliberate: .md preserves rendering in every existing markdown toolchain, while .aicc. lets engines and validators identify conforming documents by name alone, without opening the file.

3.2Encoding & Base Syntax

A document MUST be encoded as UTF-8 without BOM. A document MUST begin with a frontmatter block: an opening --- line as the first bytes of the file, terminated by the first subsequent line consisting solely of ---. The frontmatter block is stripped before the body is parsed; lines consisting solely of --- MUST NOT appear inside frontmatter values. The body — everything after the closing delimiter — MUST be valid CommonMark 0.31 or later.

Frontmatter MUST use the Level 1.0 YAML subset: scalar values and flow-style (inline [a, b]) sequences only. Block sequences, nested mappings, anchors, aliases, and tags are outside the subset (error E104, § 10.3). This keeps every conforming frontmatter block parseable by a 30-line parser in any language.

Canonical sections (§ 5) MUST use ATX level-2 headings (## Name). Setext headings MUST NOT be used for canonical sections.

Engines MUST NOT attach AICC semantics to any construct not defined in this specification. Unknown @aicc annotations MUST be ignored and MUST NOT cause parsing to fail (forward compatibility) — but they do not satisfy any annotation requirement of this specification (§ 7, § 10.1).

4Frontmatter Schema

4.1Required Keys

KeyTypeConstraint
aiccstringThe specification level this document targets, e.g. "1.0". Engines MUST reject documents declaring a major level they do not implement.
kindenumOne of product-spec, feature-spec, agent-config, architecture, constraint-set. Determines which canonical sections are required (§ 5).
idstringReverse-DNS identifier, globally unique per document lineage, e.g. com.example.checkout. MUST match ^[a-z0-9]+(\.[a-z0-9-]+)+$.
versionstringSemantic version (SemVer 2.0.0) of the specified product or document content — not of the AICC level.

4.2Optional Keys

KeyTypeMeaning
conformanceenumbasic | strict. The class the author claims; validators verify the claim (§ 10). Default: basic.
enginesstring[]Engine identifiers from the AICC Engine Registry this document has been exercised against. Informative — absence MUST NOT cause an engine to refuse the document.
extendsstringRelative path or id of a parent document whose sections this document inherits (§ 9).
scopestring[]Glob patterns limiting which paths this document governs, e.g. ["src/checkout/**"]. Empty means repository-wide.
ownerstringAccountable team or person. Informative.
updateddateISO-8601 date of last substantive change. Informative.
context-excludestring[]Repository-relative globs naming generated, vendored, or bulk content that engines should never load as context (§ 4.3). Same syntax and validation as scope.
context-primestring[]An ordered list of at most 8 paths an engine SHOULD read first when establishing project context (§ 4.3).

Validators MUST reject unknown top-level frontmatter keys unless they are prefixed with x-. The x- namespace is reserved for private extensions and MUST be ignored by engines that do not recognise them.

4.3Context Directives

The most expensive thing an engine does is discovering what not to read. Every engine re-learns, every session, that dist/, lockfiles and fixtures are noise. Context directives turn that per-session exploration into a single frontmatter read.

Engines MUST NOT load content matched by context-exclude into model context unless the end user explicitly requests it or the engine is directly editing a matched file. context-exclude is a context directive, not an access restriction: it never forbids reads required to complete a task; it declares them unnecessary. Paths matched by both scope and context-exclude remain governed by this document's requirements.

When establishing project context, engines SHOULD read the context-prime paths first, in the order given, before any speculative exploration. Invalid globs in either key are reported as E502 (§ 10.3).

context-exclude: ["dist/**", "node_modules/**", "*.lock", "fixtures/**"]
context-prime: ["README.md", "src/checkout/index.ts", "docs/architecture.md"]

5Section Taxonomy

AICC defines a closed set of canonical top-level (##) sections. Canonical names give engines a stable addressing scheme: an engine can ask "what are the Requirements?" and get a deterministic answer on any conforming document in any repository.

SectionDefault classPurpose
## OverviewInformativeWhat the product/feature is and why it exists. Prose.
## RequirementsNormativeWhat the product must do. One requirement per list item (§ 6).
## ConstraintsNormative (directives)How engines must behave while working in this scope (§ 8).
## ArchitectureInformativeStructure, boundaries, key decisions and their rationale.
## InterfacesNormativePublic contracts: APIs, schemas, events, CLI surfaces.
## Non-GoalsNormativeExplicitly out of scope. Engines MUST NOT implement features listed here.
## GlossaryInformativeDomain terms used with precise meaning in this document.

A document of kind product-spec or feature-spec MUST contain ## Overview and ## Requirements. A document of kind agent-config or constraint-set MUST contain ## Constraints. Additional non-canonical sections MAY appear; they default to informative unless annotated otherwise (§ 7).

6Requirement Keywords

6.1The One-Item-One-Keyword Rule

Inside a normative section, each requirement MUST be a single top-level list item — any CommonMark list marker (-, *, +, or an ordered marker) — containing exactly one all-capitals RFC-2119 keyword. Nested list items elaborate their parent requirement and MUST NOT contain RFC-2119 keywords. A top-level list item in a normative section containing zero keywords, or more than one, is a validation error in class strict (§ 10) and a warning in class basic.

Engines MUST treat MUST / MUST NOT requirements as hard constraints: output that violates one is non-conforming regardless of any other instruction except an override under precedence rules 1 or 2 (§ 8.2). SHOULD requirements are defaults an engine departs from only with stated reason. MAY marks explicitly granted freedom.

- Payments MUST be idempotent per order id.        ← one item, one keyword ✓
- The API MUST NOT expose card data.             ← negation is one keyword ✓
- Use retries and MUST log failures somewhere.     ← prose + keyword mix ✗ E301

Rationale: "one item, one keyword" makes every requirement individually addressable, testable, and diffable. It is the single highest-leverage rule in this specification — it turns prose into a checklist an engine can prove it satisfied.

6.2Requirement Identifiers

A requirement MAY begin with a requirement identifier: a bracketed token matching ^\[[A-Z][A-Z0-9]{0,7}-[0-9]{1,5}\] immediately after the list marker, e.g. - [REQ-012] Payments MUST be idempotent per order id.

Identifiers MUST be unique within the effective composed document (§ 9). Once published, an identifier MUST NOT be reused for a different requirement; edit a requirement's text in place, and retire its identifier when the requirement is removed. In class strict, if any requirement in a normative section carries an identifier, all requirements in that section MUST carry one (E303, § 10.3).

Engines SHOULD reference requirements by id + identifier (e.g. com.example.checkout#REQ-012) when reporting compliance, conflicts, or precedence decisions, instead of re-quoting requirement text.

Identifiers are what make requirements addressable like test names: engines can keep a compact satisfied/violated ledger across a long task, diff requirement sets between document versions, and emit auditable compliance claims ("satisfies REQ-012") that teams can grep.

7Annotations

Annotations assign a machine-readable class to a section. They are HTML comments, so every markdown renderer hides them and no human reader is disturbed.

An annotation MUST appear on the same line as, or the line immediately following, an ATX level-2 (##) heading, and applies to that section until the next level-1 or level-2 heading. Deeper headings (### and below) inherit the class of their enclosing section and MUST NOT carry annotations (E401). Recognised annotations in Level 1.0:

AnnotationEffect
<!-- @aicc:normative -->Section contains requirements; § 6 rules apply.
<!-- @aicc:informative -->Section is context only. Engines MUST NOT derive requirements from it.
<!-- @aicc:directives -->Section contains engine directives (§ 8).
<!-- @aicc:example -->Illustrative material. Engines MUST NOT treat examples as exhaustive or binding.
<!-- @aicc:deprecated since="2.0.0" -->Section retained for history. Engines MUST ignore its requirements and SHOULD warn if asked to implement them.

Canonical sections carry the default class of § 5 without annotation; an explicit annotation on a canonical section overrides its default.

8Agent Directives

8.1Semantics

A directive is a requirement addressed to the engine: which commands to run, which paths may be modified, which behaviours are forbidden. Directives live in ## Constraints or any section annotated @aicc:directives, and use the same keyword grammar as § 6 with the engine as the implied subject. 

## Constraints <!-- @aicc:directives -->
- Engines MUST run `pnpm test` before proposing a commit.
- Engines MUST NOT modify files under `migrations/`.
- Engines MAY refactor freely within `src/checkout/`.

8.2Precedence Model

When instructions conflict, engines MUST resolve in this order, highest first:

  1. The engine's own safety policies and applicable law.
  2. An explicit, contemporaneous instruction from the end user.
  3. MUST / MUST NOT directives of the nearest governing document (§ 9).
  4. MUST / MUST NOT directives of ancestor documents.
  5. SHOULD-level directives, nearest first.
  6. Engine defaults.

An engine that overrides a MUST-level directive on the basis of rule 1 or 2 SHOULD state that it has done so and why.

Trust boundary. Proximity is not provenance. Engines MUST honour directives only from documents inside the trust root the invoker selected (normally the repository the user opened). Documents introduced by untrusted contributions — third-party pull requests, vendored dependencies, submodules, downloaded templates — MUST NOT contribute directives until a trusted party has reviewed them, and engines SHOULD surface newly added or modified directives to the user before honouring them (see § 12). An extends reference resolves only within the repository; it MUST NOT trigger a network fetch.

This ordering is deliberately identical in spirit to how existing engines already resolve user-versus-project-file conflicts; AICC standardises the behaviour rather than inventing it.

9Inheritance & Composition

Documents discovered along the directory chain of § 3.1 form an implicit composition chain, root first, nearest last — exactly as if each document declared extends on its nearest discovered ancestor. The extends key is needed only to compose with a document outside the discovery path (e.g. a shared, organisation-wide constraint-set); declaring extends on a document already in the implicit chain is redundant and MUST NOT change the merge result.

A child document inherits every section of its parents. A child section with the same canonical name MUST be interpreted as augmenting the parent section, not replacing it, except that a child requirement that directly contradicts a parent requirement MUST take precedence within the child's scope.

Composition chains (implicit plus extends) MUST be acyclic and MUST NOT exceed a depth of 8. Engines MUST apply the most specific document whose scope matches the path being worked on; documents with non-matching scope MUST NOT contribute requirements to that path. The governing document for a path is the scope-matching document deepest in the composition chain; among scope-matching documents at equal depth, the one with the more specific matching glob governs. The effective requirement set for any path is therefore a pure function of the file tree — engines MAY compute and cache it once per session.

This mirrors the directory-cascading behaviour teams already use with nested instruction files, but makes the merge rules explicit — the historical source of "which file wins?" ambiguity.

10Conformance

10.1Conformance Classes — Documents

ClassRequirements
Basic (A)Valid frontmatter (§ 4); required canonical sections for the declared kind (§ 5); body parses as CommonMark.
Strict (AA)Basic, plus: every normative list item satisfies the one-item-one-keyword rule (§ 6); every non-canonical section is explicitly annotated (§ 7); zero validator warnings.
Certified (AAA)Strict, plus: round-trip proof through the interop mappings (§ 11) for every engine listed in engines, verified by the AICC conformance suite.

The class a document achieves is determined solely by the checks it satisfies; the conformance key states a claim and MUST NOT alter the achieved class. Validators MUST evaluate every class's check set independently of the claim and report both the claimed class and the achieved class — the highest class whose complete check set passes. The per-class severities of § 10.3 affect only how findings are reported against the claim, never which class is achieved. Certified is awarded by the consortium's conformance programme and is never claimed in frontmatter — which is why the conformance enum contains only basic and strict. The Certified class is provisional: it becomes testable only when AICC-TR-005 (Interop Mappings) reaches Candidate Recommendation.

10.2Conformance Classes — Engines

A conforming engine (1) parses every Basic-class document without loss of content, (2) honours section classes — deriving requirements only from normative sections, (3) implements the precedence model of § 8.2, and (4) implements scope matching of § 9. A conforming engine MUST pass the published engine test suite for the level it declares.

11Interop Mappings

This section is informative until AICC-TR-005 (Interop Mappings, Editor's Draft) reaches Candidate Recommendation, at which point the mapping principle below transfers there as normative text.

AICC is the source of truth; engine dialects are derived artifacts. AICC-TR-005 defines the full translation tables. The core principle:

A mapping is lossless for normative content: every requirement and directive survives translation with its keyword strength intact. Where a target dialect cannot express a construct (e.g. scope globs), the mapping emits the construct as a clearly-delimited comment so no information is silently dropped. (Normative phrasing moves to AICC-TR-005.)

TargetMapping sketch
CLAUDE.md / AGENTS.mdFrontmatter → header comment; ## Constraints → instruction body; scoped documents → nested per-directory files. Initial mapping target of AICC-TR-005.
.cursorrulesDirectives flattened to rule lines; keyword strength preserved as [MUST]/[SHOULD] prefixes.
copilot-instructions.mdNormative sections concatenated; informative sections summarised behind a marker.

12Security Considerations

  • Directive injection. AICC documents are code-adjacent configuration. Engines MUST treat directives in files sourced from untrusted contributions (e.g. third-party pull requests) with the same suspicion as untrusted code, and SHOULD surface newly added or modified directives to the user before honouring them.
  • Privilege escalation. A directive can never grant an engine a capability the invoking user does not have. The precedence model (§ 8.2) places engine safety policy above every document-level instruction.
  • Annotation spoofing. Because annotations are invisible in rendered markdown, validators SHOULD offer a mode that renders all annotations visibly for human review.
  • Scope escape. Engines MUST reject scope globs that resolve outside the repository root.

Appendix A — Complete Example

---
aicc: "1.0"
kind: product-spec
id: com.example.checkout
version: 2.3.0
conformance: strict
engines: [claude-code, cursor]
scope: ["src/checkout/**"]
owner: payments-team
updated: 2026-07-24
---

# Checkout Service

## Overview
Handles cart-to-payment conversion for all storefronts.
Talks to the PSP via the payments gateway; never directly.

## Requirements
- Payments MUST be idempotent per order id.
- The API MUST NOT expose card data in any response or log.
- Checkout MUST complete in under 2 s at p95.
- Retries SHOULD use exponential backoff with jitter.
- Currencies other than EUR MAY be rejected in v2.

## Non-Goals
- Subscription billing MUST NOT be implemented in this service.

## Constraints <!-- @aicc:directives -->
- Engines MUST run `pnpm test --filter checkout` before proposing a commit.
- Engines MUST NOT modify files under `migrations/`.
- Engines SHOULD keep functions under 40 lines.

## Glossary <!-- @aicc:informative -->
- **PSP** — Payment Service Provider.
