Abstract

This report defines bidirectional mappings between AICC Markdown (AICC Core 1.0) and the instruction dialects of registered engines. The forward direction (AICC → dialect) is normative and lossless for normative content; the reverse direction (dialect → AICC) is a reviewed heuristic, implemented by the consortium's migration tool. Third-party engine and product names appear solely to describe interoperability; no endorsement is implied in either direction.

Status of This Document

This is an Editor's Draft of the Engine Interop Working Group. It has no standing. It is published so that engine vendors can review their dialect's mapping before the document advances to Working Draft. The initial mapping target is Claude Code (§ 3); further dialect sections advance as vendor liaisons confirm them.

1Mapping Principles

A forward mapping (AICC → dialect) MUST be lossless for normative content: every requirement and directive survives translation with its RFC-2119 keyword strength and its requirement identifier (if any) intact. Informative content MAY be summarised. Where the target dialect cannot express a construct, the mapping MUST emit a loss marker (§ 2) instead of silently dropping it.

Derived files MUST begin with a generation header naming the source document and its version, so humans and engines know which file is canonical.

2Loss Markers

A construct the target dialect cannot express is emitted as an HTML comment of the form <!-- aicc:untranslated key="…" value="…" --> at the position where the construct would apply. Reverse mappings MUST restore marked constructs verbatim, which is what makes round-trips lossless even through lossy dialects.

3CLAUDE.md / AGENTS.md (Claude Code)

Because AICC Markdown is plain CommonMark, the Claude Code mapping is nearly the identity — it is the reference-quality mapping and the reason Claude Code is the initial conformance target.

FrontmatterGeneration header comment; id/version preserved inside it. Frontmatter keys without dialect equivalents get loss markers.
Body sectionsCopied verbatim — headings, keywords, requirement IDs and @aicc annotations are all valid markdown/comments in the dialect.

AICC constructMapping

7Reverse Mapping (dialect → AICC)

Reverse mappings are heuristic: legacy dialects do not carry machine-readable keyword strength. A reverse mapper MUST mark its output as a draft (conformance: basic, provenance note in ## Overview) and MUST NOT emit conformance: strict without human review. Polarity MUST be preserved when rewriting imperatives ("Never X" → "Engines MUST NOT X").

The consortium's reference implementation is plugins/aicc/scripts/migrate.mjs (the /aicc-migrate command of the Claude Code plugin). It reads CLAUDE.md, AGENTS.md, .cursorrules, .cursor/rules/*.mdc, copilot-instructions.md, GEMINI.md and .windsurfrules.

8Round-Trip Conformance

A mapping implementation is round-trip conforming for a dialect when, for every document in the conformance corpus, AICC → dialect → AICC reproduces the original effective content: identical requirement set (IDs, keyword strengths, section classes), identical directives, and identical frontmatter after loss-marker restoration. This is the test the Certified (AAA) document class of Core § 10.1 builds on.
