ADP — Agent Discovery & Policy 1.0

The discovery and policy layer for the agent-native web: how origins publish specifications, declare agent policy, and signal conformance over HTTP.

Abstract

robots.txt told crawlers where they may go. It says nothing about what an agent may do. As AI code engines become first-class consumers of websites, APIs, and repositories, every origin needs a standard way to answer three questions: Where is the specification for this thing? What is an agent allowed to do here? How do we tell each other? ADP answers all three with a human-editable policy file (agents.txt), a machine manifest (/.well-known/adp.json), and a small set of HTTP headers. Together with AICC Core 1.0, this forms the complete contract between an origin and any conforming engine.

Status of This Document

This is a Working Draft of the Engine Interop Working Group. Breaking changes are expected. It is published for early implementation feedback and is not yet a Recommendation.

1Introduction

The web's existing agent controls were designed for a read-only visitor: a crawler that fetches pages and leaves. Code engines are different in kind — they read specifications, open pull requests, call APIs, execute workflows, and act on behalf of users. Three gaps follow:

  • No discovery. An engine landing on an origin has no standard way to find the specification that governs it.
  • No policy vocabulary. robots.txt can say don't fetch; it cannot say read, but never execute or propose changes, but only under this spec.
  • No signalling. Origins and engines cannot identify each other's capabilities or conformance levels in-band.

ADP fills these gaps with deliberately boring technology: a line-based text file, a JSON document at a well-known URI (RFC 8615), and HTTP header fields — each layered so that adopting the first requires five minutes and a text editor.

2Terminology

The key words MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are to be interpreted as described in RFC 2119. Engine and Document are defined in AICC Core § 2. An Origin is a scheme/host/port triple as defined in RFC 6454. An Action class is one of the verbs defined in § 3.1.

3Discovery Layer

3.1agents.txt

An origin that adopts ADP MUST serve a UTF-8 text file at /.well-known/agents.txt (per RFC 8615) and MAY also serve it at the legacy-friendly root path /agents.txt; when both exist, the well-known resource wins. The file is line-based; each line is a Field: value pair, # starts a comment. Records begin with an Engine: line naming an engine identifier from the AICC Engine Registry, or * for all engines. Fields apply to the most recent Engine: record.

FieldMeaning
Engine:Starts a record. An identifier from the public AICC Engine Registry, a reverse-DNS identifier for unregistered engines (e.g. com.example.mybot), or *.
Spec:Path or URL of the governing AICC document. Repeatable.
Allow: / Disallow:Grants or forbids an action class: read, propose (suggest changes, open PRs), write (direct mutation), execute (run code/API calls with side effects).
Policy:URL of the machine manifest (§ 3.2).
Contact:mailto: or URL for the humans responsible for agent traffic.

The four action classes form an escalation ladder. A grant of a higher class MUST NOT be interpreted as an implicit grant of a lower one — each class is declared explicitly. In the absence of an agents.txt and manifest, the default policy for autonomous agent activity is Allow: read and nothing else; an explicit, contemporaneous end-user instruction always overrides origin policy (see § 5).

Merging is per action class, never per field. An engine-specific record overrides the * record only for the action classes it explicitly names; every class it does not mention is inherited from the * record. In the example below, the effective policy for claude-code is therefore read, propose (inherited) plus execute (granted) — the record adds rope, it does not revoke the baseline.

# agents.txt — ADP/1.0
Engine: *
Spec: /product.aicc.md
Policy: /.well-known/adp.json
Allow: read
Allow: propose
Disallow: execute
Contact: mailto:agents@example.com

# CI bots get more rope
Engine: claude-code
Allow: execute

3.2/.well-known/adp.json

The manifest is the machine-grade version of agents.txt: same semantics, richer structure, JSON syntax. When both exist and disagree, the manifest wins (§ 5). 

{
  "adp": "1.0",
  "specs": [
    { "href": "/product.aicc.md", "id": "com.example.shop", "scope": ["/**"] }
  ],
  "policies": [
    { "engine": "*", "allow": ["read", "propose"], "disallow": ["write", "execute"] },
    { "engine": "claude-code", "allow": ["execute"] }
  ],
  "rate": { "requests_per_minute": 120 },
  "contact": "mailto:agents@example.com"
}

3.3Repository Discovery

Inside a repository (as opposed to an HTTP origin), discovery follows AICC Core § 3.1 unchanged: the most specific scope-matching document governs, and documents compose per Core § 9; the root product.aicc.md is the repository-wide fallback when no nearer document's scope matches. A repository MAY additionally carry an agents.txt at its root with identical semantics, governing engines that operate on the repository through any transport.

4HTTP Signalling

4.1Request Headers (engine → origin)

HeaderMeaning
Agent-ProfileA URI identifying the engine and the ADP level it implements, e.g. https://registry.aicodingconsortium.org/engines/claude-code#adp-1.0. Analogous in spirit to the profile mechanism of RFC 9110 content negotiation.
Agent-IntentThe action class this request belongs to: read, propose, write, or execute. Lets origins enforce policy at the edge, per request.

A conforming engine MUST send both headers on every request to an origin whose policy it has read. Acting autonomously, an engine MUST NOT issue a request whose Agent-Intent the origin's effective policy disallows. Acting on an explicit, contemporaneous end-user instruction, the engine MAY proceed despite a disallow — mirroring rule 2 of the precedence ladder in AICC Core § 8.2 — and SHOULD tell the user it is overriding origin policy. The engine's own safety policy (rule 1) sits above both.

4.2Response Headers (origin → engine)

HeaderMeaning
Spec-LocationURL of the governing AICC document for the requested resource, e.g. Spec-Location: /product.aicc.md. The HTTP-level equivalent of Spec: in agents.txt, resolvable per-path.
Agent-PolicyEffective policy for the requesting engine in compact form: Agent-Policy: allow=(read propose), disallow=(write execute).
ADP-VersionThe ADP level the origin implements: ADP-Version: 1.0.

Origins MAY answer a disallowed request with status 403 and SHOULD include Agent-Policy in that response so the engine can self-correct instead of retrying.

4.3HTML-Level Signalling

For static hosting where headers are impractical, the same information MAY be embedded in markup:

<link rel="spec" type='text/markdown; variant="AICC"' href="/product.aicc.md">
<meta name="adp:policy" content="disallow=write execute">

AICC documents use the existing text/markdown media type with the variant parameter that RFC 7763 defines for exactly this purpose (variant=AICC, plus an optional level parameter). AICC-TR-007 (forthcoming) specifies the variant registration submitted to IANA's markdown-variants registry. Per § 5, HTML-level signalling can only narrow policy, so adp:policy markup carries disallow lists only.

5Precedence & Merging

Policy sources form a narrowing-only ratchet. The manifest (/.well-known/adp.json) — or, absent a manifest, agents.txt — is the grant ceiling for an origin. Per-response HTTP headers (§ 4.2) and HTML-level signalling (§ 4.3) MUST NOT grant an action class the ceiling does not already grant; they MAY only remove classes for the current resource or request. Any grant of write or execute MUST originate from a manifest or agents.txt fetched over HTTPS from the same origin.

Evaluation order for a given request:

  1. Start from the grant ceiling: manifest if present, else agents.txt, else the default (read only for autonomous activity).
  2. Merge engine-specific records per action class (§ 3.1): unmentioned classes inherit from *.
  3. Apply per-response narrowing from headers and markup — remove classes only.

The layers are: (1) the grant ceiling (manifest or agents.txt) and (2) per-response narrowing (headers, markup). Within the ceiling, engine-specific records merge per action class as defined in § 3.1 — an explicit engine-record declaration replaces the * declaration for that class, which is how a record can add execute on top of the baseline. After that merge, a Disallow for a class defeats an Allow for the same class within a single record or from any lower layer. Origin policy governs autonomous engine activity; its place relative to user instructions and engine safety policy is defined in § 4.1.

6Caching

Engines MUST honour standard HTTP caching for agents.txt and adp.json. Absent cache metadata, engines MUST NOT cache policy longer than 24 hours and SHOULD re-fetch before any write or execute action. A newly fetched, more restrictive policy applies immediately, including to in-flight plans.

7Conformance

ClassRequirements
Conforming originServes a syntactically valid agents.txt; every Spec: target is a Basic-class AICC document; manifest (if present) validates against the ADP JSON Schema.
Conforming engineDiscovers policy in § 5 order; sends § 4.1 headers; never performs a disallowed action class; passes the ADP engine test suite.

8Security Considerations

  • Policy is not access control. ADP is a declaration of intent, honoured by conforming engines. Origins MUST NOT rely on it as a security boundary and MUST keep enforcing authentication and authorization independently — exactly as robots.txt never replaced access control.
  • Policy injection. A compromised agents.txt could grant execute to lure engines into destructive actions. Engines SHOULD treat policy upgrades (new grants of write/execute) as events to surface to their user, and MUST apply the precedence rule that their own safety policy sits above any origin grant (AICC Core § 8.2).
  • Fingerprinting. Agent-Profile identifies engine software, not users. Engines MUST NOT embed user-identifying data in it.
  • Cross-origin spec references. A Spec: pointing at a foreign origin MAY be fetched, and only under all of these conditions: HTTPS only; no redirects to a third origin; no private, loopback, or link-local address targets; a response-size cap. Content fetched cross-origin is informative only — it MUST NOT contribute directives or requirements, preventing both third-party steering and the use of agents.txt as an SSRF vector.

Appendix A — Complete Example

A shop that lets any engine read and propose, lets one engine execute, and publishes its spec at the root:

GET / HTTP/1.1  →  200 OK
ADP-Version: 1.0
Spec-Location: /product.aicc.md
Agent-Policy: allow=(read propose), disallow=(write execute)

— /.well-known/agents.txt — (root /agents.txt may mirror it)
Engine: *
Spec: /product.aicc.md
Policy: /.well-known/adp.json
Allow: read
Allow: propose
Disallow: write
Disallow: execute
Contact: mailto:agents@example.com

# engine-specific record: adds execute on top of the * baseline (§ 3.1 merge)
Engine: claude-code
Allow: execute

# effective policy for claude-code: read, propose (inherited) + execute (granted)
# effective policy for all other engines: read, propose

Appendix B — Manifest JSON Schema (Normative)

{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "https://spec.aicodingconsortium.org/adp/1.0/manifest.json",
  "type": "object",
  "required": ["adp"],
  "$defs": { "action": { "enum": ["read", "propose", "write", "execute"] } },
  "properties": {
    "adp":      { "type": "string", "pattern": "^1\\.[0-9]+$" },
    "specs":    { "type": "array", "items": { "type": "object", "required": ["href"], "properties": { "href": {"type": "string"}, "id": {"type": "string"}, "scope": {"type": "array", "items": {"type": "string"}} } } },
    "policies": { "type": "array", "items": { "type": "object", "required": ["engine"], "properties": { "engine": {"type": "string"}, "allow": {"type": "array", "items": {"$ref": "#/$defs/action"}}, "disallow": {"type": "array", "items": {"$ref": "#/$defs/action"}} } } },
    "rate":     { "type": "object", "properties": { "requests_per_minute": {"type": "integer", "minimum": 1} } },
    "contact":  { "type": "string" }
  },
  "additionalProperties": false
}
