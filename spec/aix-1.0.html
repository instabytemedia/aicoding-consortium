AICC Technical Report 008

AIX — Agent Content Index 1.0

The agent-native successor to sitemap.xml: know what a page contains, what it costs, and whether it changed — before fetching it.

Abstract

sitemap.xml tells a crawler which URLs exist. It says nothing about what they contain, what reading them costs, or whether they changed since the last visit — so agents crawl blind, re-reading unchanged pages and discovering irrelevance only after spending the tokens. AIX defines /.well-known/aix.json: a content index carrying, per URL, a 280-character summary, a content hash, a token-cost estimate, a content type, and optional stable chunk identifiers. With it, an agent plans its reading before its first content fetch, revalidates a whole site in one request, and re-fetches only what changed.

Status of This Document

This is an Editor's Draft of the Engine Interop Working Group. It has no standing and will change. It is published early because the format is deliberately small enough to implement in an afternoon — implementation feedback is the input the draft needs most. AIX is layer 4 of the Agent Web Stack.

1Introduction

Reading the web costs an agent three things it can rarely predict:

  • Relevance risk. Whether a URL contains what the task needs is discovered only after fetching and parsing it.
  • Token cost. A URL might be a 400-token changelog or a 150,000-token API reference. The agent finds out at the most expensive possible moment.
  • Staleness risk. Nothing tells an agent whether a page changed since its last visit, so safe behaviour means re-reading everything.

AIX moves all three answers in front of the fetch, in one machine-readable file that any static site can generate at build time. The design constraint is the same one that made sitemap.xml and robots.txt universal: adopting it requires a text file, not a backend.

2Location & Discovery

An origin that adopts AIX MUST serve the index as UTF-8 JSON at /.well-known/aix.json. Origins SHOULD additionally declare it via the Index: field in agents.txt and the index member of /.well-known/adp.json — both registered by this report as ADP 1.0 extensions; conforming ADP parsers ignore unknown fields, so the declarations are backward-compatible.

Fetching the index is a read-class action under ADP § 3.1 and requires no grant beyond the default.

3Index Format

The top-level object:

MemberTypeConstraint
aixstringRequired. The AIX level, e.g. "1.0".
originstringRequired. The origin this index describes. Engines MUST ignore an index whose origin does not match the origin it was fetched from.
generatedstringRequired. ISO-8601 timestamp of generation.
previousstringOptional. URL of the previous snapshot (§ 6).
entriesarrayRequired. One entry per indexed resource.

Each entry:

MemberTypeConstraint
urlstringRequired. Absolute path or absolute URL on origin.
titlestringRequired. Human title of the resource.
summarystringRequired, ≤ 280 characters. What the resource contains — written for an agent deciding whether to fetch, not for marketing.
hashstringRequired. sha256- prefix + lowercase hex SHA-256 of the resource's extracted text content (§ 3.1).
tokensintegerRequired. Estimated token cost of the resource's text representation. An estimate, not a contract; § 5 defines how engines may rely on it.
updatedstringRequired. ISO-8601 date of last content change.
typeenumRequired. docs | product | article | api | ugc. Content bearing third-party text is ugc.
chunksarrayOptional. Stable sub-resource addresses (§ 4).

3.1Text Extraction

The hash input is the resource's extracted text: for HTML, the text content of the document body after removing script, style, and comment nodes, with whitespace runs collapsed to single spaces and leading/trailing whitespace trimmed; for markdown and plain text, the raw file with the same whitespace normalisation. This definition makes the hash reproducible across independent implementations and insensitive to markup-only changes.

4Chunk Addressing

Long resources deserve sub-addressing: an agent that needs one section of an API reference should not re-read the other 140,000 tokens. Each chunk entry is { "id": "…", "hash": "sha256-…", "tokens": n }.

A chunk id MUST be a valid URL fragment for the entry's resource (for HTML, an element id; for markdown, a heading slug), and MUST remain stable across revisions while the chunk's topic persists — the same immutability rule AICC Core § 6.2 applies to requirement identifiers. Chunk hashes use the § 3.1 extraction applied to the chunk's own text.

Chunk addressing is the seed of AICC-TR-010; AIX 1.0 carries only what an index needs. Engines cite a chunk as <url>#<id> — an address a human can open in a browser, unchanged.

5Engine Behaviour

An engine that has fetched an origin's index MUST NOT re-fetch a resource whose hash is unchanged from the version the engine has already processed, unless the end user explicitly requests a re-read (differential crawling). Engines SHOULD use summary, type, and tokens to plan reading order under their context budget before the first content fetch, and SHOULD prefer chunk fetches over full-resource fetches when the needed chunk is identifiable.

Index values are claims, not proofs. Engines SHOULD verify the hash of at least one fetched resource per session against the index and MUST fall back to normal crawling for an origin whose index proves unreliable (§ 8). A missing or invalid index never makes an origin unreachable — AIX is an accelerator, not a gate.

6Snapshots & Deltas

An origin MAY publish dated snapshots (e.g. /.well-known/aix/2026-07-24.json) and reference the prior one via previous. An engine holding any older snapshot computes "what changed" by comparing entry hashes — one conditional request (standard HTTP caching applies to the index itself) answers it for the whole origin. Snapshot chains SHOULD be retained for at least 90 days.

7Conformance

ClassRequirements
Index AThe index validates against the Appendix B schema; origin matches; every url resolves on the origin.
Index AAClass A, plus: hashes verify against § 3.1 extraction for a random sample drawn by the conformance suite; updated dates are consistent with observed changes across two suite runs.
Conforming engineImplements the § 5 behaviour, including differential crawling and unreliable-index fallback.

8Security Considerations

  • Index poisoning. A malicious index could hide changed content behind a stale hash (suppressing re-reads) or inflate tokens to discourage scrutiny. Hence § 5's spot-check duty and unreliable-index fallback: one failed verification and the index loses its authority for that origin.
  • Summaries are untrusted text. A summary is origin-authored content and MUST be treated as data, never as instructions to the engine — the ADP § 9.3 trust rule applies to index metadata exactly as to page content.
  • UGC labelling. Mislabelling ugc as first-party is the index-level variant of trust-label spoofing; engines SHOULD apply UGC handling to content that heuristically looks third-party even when the index claims otherwise.
  • Privacy. Indexes enumerate content; origins MUST NOT list resources that are access-controlled, and engines MUST NOT treat a listed URL as an access grant — ADP policy still governs.

Appendix A — Complete Example

{
  "aix": "1.0",
  "origin": "https://example.com",
  "generated": "2026-07-24T12:00:00Z",
  "previous": "/.well-known/aix/2026-07-17.json",
  "entries": [
    {
      "url": "/docs/api",
      "title": "REST API Reference",
      "summary": "All 42 endpoints with request/response schemas, auth (OAuth2), rate limits, error codes.",
      "hash": "sha256-9f2c…",
      "tokens": 148000,
      "updated": "2026-07-20",
      "type": "api",
      "chunks": [
        { "id": "auth", "hash": "sha256-11ab…", "tokens": 3200 },
        { "id": "orders-api", "hash": "sha256-c04d…", "tokens": 5900 }
      ]
    },
    {
      "url": "/blog/launch",
      "title": "Launch announcement",
      "summary": "Marketing post announcing v2. No technical content.",
      "hash": "sha256-77e1…",
      "tokens": 900,
      "updated": "2026-06-30",
      "type": "article"
    }
  ]
}

An agent researching "how does auth work" now fetches exactly one 3,200-token chunk instead of crawling the site — and next week, one index request tells it nothing changed.

Appendix B — JSON Schema (Normative)

{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "https://spec.aicodingconsortium.org/aix/1.0/index.json",
  "type": "object",
  "required": ["aix", "origin", "generated", "entries"],
  "properties": {
    "aix":       { "type": "string", "pattern": "^1\\.[0-9]+$" },
    "origin":    { "type": "string", "format": "uri" },
    "generated": { "type": "string" },
    "previous":  { "type": "string" },
    "entries": {
      "type": "array",
      "items": {
        "type": "object",
        "required": ["url", "title", "summary", "hash", "tokens", "updated", "type"],
        "properties": {
          "url":     { "type": "string" },
          "title":   { "type": "string" },
          "summary": { "type": "string", "maxLength": 280 },
          "hash":    { "type": "string", "pattern": "^sha256-[0-9a-f]{64}$" },
          "tokens":  { "type": "integer", "minimum": 0 },
          "updated": { "type": "string", "pattern": "^\\d{4}-\\d{2}-\\d{2}$" },
          "type":    { "enum": ["docs", "product", "article", "api", "ugc"] },
          "chunks":  {
            "type": "array",
            "items": {
              "type": "object",
              "required": ["id", "hash"],
              "properties": {
                "id":     { "type": "string" },
                "hash":   { "type": "string", "pattern": "^sha256-[0-9a-f]{64}$" },
                "tokens": { "type": "integer", "minimum": 0 }
              }
            }
          }
        }
      }
    }
  },
  "additionalProperties": false
}
